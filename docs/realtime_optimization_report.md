# 小车实时性与角速度环优化方案报告

> 用途：这是一份“先分析、再审批、后实施”的优化方案文档。  
> 当前文档只讨论优化方向和验证方法，不代表所有建议都必须一次性修改。

## 1. 问题背景

当前现象可以概括为：单独测试 MPU6050 很快，但小车主程序运行时，角速度环仍然会出现数据变旧、定时器超时、车辆响应变慢等问题。

| 观察项 | 现象 | 初步含义 |
|---|---|---|
| 单独读取 MPU6050 | `gyro_read_benchmark` 中 `avg≈0.190ms`，`max≈0.292ms` | I2C/ioctl 本身足够快 |
| 主程序运行 | 日志中曾出现 gyro read 超时、`age` 变大、`I_freeze=1` | 问题更像是主程序负载和线程调度 |
| 控制需求 | 角速度环希望 8ms~10ms 级别稳定运行 | 需要保证控制相关线程及时被调度 |
| 当前主程序 | 图像处理、VOFA、UDP 图传、TFT、多个 `lq_timer`、日志并行运行 | 高负载时会抢 CPU、总线和内核调用资源 |

核心结论：

| 结论 | 说明 |
|---|---|
| MPU6050 本体不是主要瓶颈 | 单独 benchmark 已经证明一次读取小于 1ms |
| 当前主要瓶颈是系统实时性 | 普通 Linux 用户态线程在高 CPU 负载下不能保证 5ms/8ms 必达 |
| 优化目标不是“读陀螺仪更快” | 而是让控制环少被图像、显示、网络和日志拖住 |
| 第一阶段应优先做低风险减负 | 先减少日志、TFT flush、图传频率，再考虑线程优先级和架构重构 |

## 2. 从底层原理分析

### 2.1 MPU6050 数据刷新原理

MPU6050 内部会按设置的采样率持续刷新角速度寄存器。当前驱动初始化中设置了较高采样率，用户层读取时只是通过 I2C 把当前寄存器值取出来。

| 项目 | 当前设计 | 对实时性的影响 |
|---|---|---|
| 陀螺仪量程 | `±2000dps` | 对应比例约 `16.4 LSB/(deg/s)` |
| 采样率 | 驱动中设置 `1000Hz` | 传感器内部理论 1ms 左右刷新一次 |
| 低通滤波 | 驱动中 LPF 约 `98Hz` | 抑制高频噪声，但会带来少量相位滞后 |
| 用户读取 | `get_mpu6050_ang()` 读取三轴角速度 | 读取动作本身只需要很短时间 |

重要理解：

| 概念 | 解释 |
|---|---|
| 传感器采样周期 | MPU6050 自己更新寄存器的频率 |
| 用户层读取周期 | 主程序多久调用一次 `get_mpu6050_ang()` |
| 控制环周期 | 方向环多久根据最新数据更新一次电机目标 |
| 数据年龄 | 当前控制使用的数据距离上次真实刷新过了多久 |

即使 MPU6050 内部 1ms 更新一次，如果主程序线程 50ms 没有被调度，那么控制环看到的数据年龄仍然会变成 50ms。  
这就是“传感器很快，但控制里数据变旧”的关键原因。

### 2.2 I2C/ioctl 路径原理

当前用户层调用大致链路如下：

```text
gyro reader thread
    -> lq_i2c_mpu6050::get_mpu6050_ang()
        -> ioctl(fd, I2C_GET_MPU6050_ANG, data)
            -> mpu6050_get_gyro_data()
                -> i2c_read_regs()
                    -> i2c_transfer()
```

| 层级 | 做什么 | 可能慢在哪里 |
|---|---|---|
| C++ 封装 | 调用 `ioctl`，把数据复制出来 | 基本不会成为主要瓶颈 |
| 字符设备驱动 | 根据命令读取 MPU6050 寄存器 | 如果驱动被阻塞，会导致 ioctl 变慢 |
| I2C 控制器 | 发送寄存器地址，再读 6 字节 | 若总线异常、驱动异常，可能变慢 |
| 用户线程调度 | 线程什么时候拿到 CPU | 高负载时最容易出现抖动 |

根据当前 benchmark：

| 测试 | 结果 | 结论 |
|---|---:|---|
| 单独读取 100 次 | `avg≈0.190ms` | ioctl + I2C 正常 |
| 最大读取时间 | `max≈0.292ms` | 没有出现 100ms 级别硬件阻塞 |
| 失败次数 | `fail=0` | 设备通信稳定 |

因此，当前优化不应优先怀疑 I2C 线速或 MPU6050 硬件，而应优先看主程序负载和线程调度。

### 2.3 Linux 用户态调度原理

普通 Linux 程序不是硬实时系统。即使你创建了一个 5ms 的定时器线程，也只能表示“希望大约 5ms 执行一次”，不能保证每次都准时。

| 情况 | 会发生什么 |
|---|---|
| CPU 很空 | 线程通常能接近目标周期运行 |
| CPU 接近满载 | 控制线程可能排队等待 CPU |
| 其他线程频繁打印 | 终端输出和 flush 会占用时间 |
| 图像处理耗时波动 | 控制线程调度延迟会变大 |
| 内核 ioctl 很多 | 线程可能在内核态和用户态之间频繁切换 |

对小车控制来说，问题不只是平均耗时，而是最大延迟。

| 指标 | 对控制的意义 |
|---|---|
| 平均耗时 | 说明系统大多数时候忙不忙 |
| 最大耗时 | 决定是否会突然失控或明显晃动 |
| 数据年龄 | 说明角速度反馈是不是新鲜 |
| 定时器超时次数 | 说明控制线程是否被拖慢 |

小车控制最怕的不是“每次都慢一点”，而是“偶尔突然慢很多”。  
例如一次 80ms 卡顿，可能已经足够让方向环错过多次更新。

### 2.4 `lq_timer` 当前工作方式

当前 `lq_timer` 的核心逻辑是：

```text
记录开始时间
执行 callback
记录结束时间
如果 callback 用时 < 目标周期：sleep 剩余时间
如果 callback 用时 > 目标周期：打印超时汇总，不补 sleep
进入下一轮
```

| 特性 | 影响 |
|---|---|
| 回调不被强杀 | 某次 callback 卡住时，该 timer 线程只能等它结束 |
| 超时后不补跑 | 不会一次性追赶多次控制，但下一轮已经被推迟 |
| 每个 timer 一个线程 | 多个毫秒级 timer 会互相竞争 CPU |
| 普通线程调度 | 没有硬实时保证 |

当前主程序相关周期：

| 模块 | 周期 | 作用 | 风险 |
|---|---:|---|---|
| 编码器采样 | `1ms` | 更新编码器速度 | 周期非常紧，容易超时 |
| 速度环 | `3ms` | 根据目标速度控制 PWM | 负载高时会被推迟 |
| gyro service | `5ms` | 检查 gyro reader 状态 | 不直接读硬件，风险较低 |
| 方向环 | `8ms` | 根据视觉误差或角速度环输出差速 | 对行驶稳定性影响大 |
| UDP 图传 | `10ms` | 发送调试图像或数据 | 图像编码时风险高 |

## 3. 当前角速度环控制链路

当前角速度环已经从“方向环同步读硬件”改成了“后台读缓存，方向环只读缓存”。这是正确方向。

```text
lq_timer 5ms
    -> gyro_yaw_rate_control_service()
        -> 确保 gyro reader thread 已启动
        -> 检查读取是否超时

gyro reader thread
    -> get_mpu6050_ang()
    -> 计算 read 用时
    -> 转换 gz 为 deg/s
    -> 做一阶低通
    -> 写入 gyro cache

dir_timer 8ms
    -> PID_control_test(latest_error)
        -> gyro_yaw_rate_control_update(error)
            -> 视觉 error 变目标角速度
            -> 读取 gyro cache
            -> 角速度 PI 输出左右轮差速
```

| 设计点 | 当前状态 | 评价 |
|---|---|---|
| 硬件读取与方向环解耦 | 已完成 | 正确，避免 ioctl 直接卡住方向环 |
| 常驻 reader 线程 | 已完成 | 比每次新建 detached worker 更稳 |
| 数据新鲜度判断 | 已有 `gyro_age_ms` | 很适合调试 |
| 旧数据处理 | 数据旧时冻结 I，不切回视觉 PD | 符合之前讨论的控制策略 |
| 超时诊断 | 已有 `timeout_count`、read min/avg/max | 方便定位 |

需要注意：

| 问题 | 说明 |
|---|---|
| reader 常驻不代表一定准时 | 如果 CPU 高负载，reader 线程仍可能迟迟拿不到 CPU |
| 缓存架构只能隔离硬件阻塞 | 不能解决系统整体 CPU 被图像/显示/日志占满 |
| `stale` 阈值过紧会频繁冻结积分 | 当前如果设为 30ms，高负载下可能太敏感 |

## 4. 根因分析

### 4.1 日志与 `printf/std::cout` 的影响

实时控制中，打印不是免费的。尤其是 `std::endl`，它不仅换行，还会强制 flush 输出缓冲区。

| 打印方式 | 风险 |
|---|---|
| `printf` 高频打印 | 占 CPU，终端慢时会拖住线程 |
| `std::cout << std::endl` | 会强制 flush，比普通换行更容易卡 |
| timer 回调里打印 | 可能让超时更加严重 |
| 内核 `printk` 高频打印 | 会影响系统整体调度 |

当前建议：

| 建议 | 原因 |
|---|---|
| 默认关闭环岛等高频路径里的 `cout` | 这些信息调车时有用，上车跑时干扰实时性 |
| 把 `std::endl` 改成 `'\n'` 或限频打印 | 避免每次强制 flush |
| `[DIR]`、`[GYRO]` 改成更低频 | 保留调试能力，但不刷屏 |
| 超时日志保留汇总 | 真出问题时还能知道发生过 |

### 4.2 TFT18 刷屏的影响

当前 TFT18 底层很多绘制函数都会在函数末尾立即 `ioctl(...FLUSH)`。  
如果一次 UI 刷新里调用多个绘制函数，就可能产生多次 SPI 刷屏和多次 ioctl。

| 当前行为 | 风险 |
|---|---|
| `draw_ui()` 调用 `cls`、`fill_area`、多次字符串绘制 | 一次 UI 更新可能触发多次 flush |
| `front_ui_poll()` 在主循环每帧执行 | 即使有 500ms 刷新限制，也会频繁检查 GPIO |
| 刷屏走 SPI/ioctl | 会占用 CPU 和内核调用时间 |

优化方向：

| 方案 | 说明 |
|---|---|
| 内存绘制和 flush 分离 | 多次修改 framebuffer，最后只 flush 一次 |
| UI 只在状态变化或低频刷新 | 例如 500ms 或 1000ms |
| 跑车时减少 UI 动态数值刷新 | 行驶稳定比屏幕实时数字更重要 |
| 调试界面和比赛运行模式分开 | 比赛模式尽量少刷屏 |

批注区：

### 4.3 UDP 图传的影响

UDP 本身不一定慢，但当前图传路径包含 OpenCV 绘制、透视变换、JPEG 编码和网络发送。真正重的是 JPEG 编码和图像处理。

| 步骤 | 负载 |
|---|---|
| `warpPerspective` | 中等到较高 |
| `cvtColor` / 画线 / `putText` | 中等 |
| `cv::imencode(".jpg")` | 较高，且耗时波动 |
| `sendto` | 一般较轻，但网络异常时可能增加抖动 |

优化方向：

| 建议 | 说明 |
|---|---|
| `is_udp_img=0` 作为跑车默认 | 比赛/调 PID 时优先保证控制实时性 |
| 图传限帧到 5~10Hz | 调试够用，避免每帧 JPEG |
| 降低 JPEG 质量 | 减少编码和传输负载 |
| 只在需要时画调试线 | 少做无关绘制 |

### 4.4 主循环图像处理的影响

主循环每帧做相机读取、灰度转换、边线提取、角点识别、环岛/十字判断、误差计算、可选图传和目标板脚本检测。

| 模块 | 可能风险 |
|---|---|
| 相机读取 | 可能等待驱动/缓冲 |
| `process_image()` | 图像算法主负载 |
| `find_corners()` | 角点筛选负载 |
| `drive_by_update()` | 若启用目标板识别，ncnn 推理负载较高 |
| 环岛/十字判断 | 一般不重，但高频打印会放大影响 |
| 图传调试 | 可显著增加负载 |

建议恢复低频耗时统计，不要每帧打印。

| 统计字段 | 用途 |

| `corner_ms` | 角点处理是否重 |
| `drive_by_ms` | 目标板推理是否重 |
| `udp_ms` | 图传是否重 |
| `loop_total_ms` | 主循环总负载 |

### 4.5 多线程共享变量风险

当前大量控制变量使用 `volatile`。`volatile` 可以阻止编译器过度优化读写，但它不是线程同步机制。

| 变量类型 | 当前风险 |
|---|---|
| 速度目标 | 主循环、VOFA、UI、速度环都可能写 |
| 方向目标 | `latest_error` 由主循环写，方向环读 |
| PWM 输出 | 方向环、速度环、停车逻辑都可能影响 |
| 状态标志 | `car_running`、脚本状态、gyro enable 等跨线程使用 |

短期不建议大改，因为你提到交叉编译环境不能用 `std::atomic`。  
第一阶段仍以减负为主，后续可以考虑“单控制线程拥有控制变量”的架构来降低竞态。

### 5.1 P0：最先做，风险低，收益大

| 编号 | 优化项 | 原因 | 预期收益 |

## 9. 风险说明

| 风险 | 说明 | 应对 |
|---|---|---|
| 阈值放宽掩盖真实问题 | `100ms/60ms` 是调试阶段策略，不是最终目标 | 观察稳定后再逐步收紧 |
| 关闭日志后不容易定位问题 | 高频日志关掉会减少现场信息 | 保留低频汇总和手动调试开关 |
| TFT 合并 flush 可能影响显示即时性 | 屏幕不再每个绘图函数立刻刷新 | UI 本来不应参与高速控制 |
| 图传限帧影响调试流畅度 | 画面帧率下降 | 调 PID 时 5~10Hz 通常够用 |
| 提高控制线程优先级可能影响视觉 | 控制太强可能让图像线程变慢 | 先做减负，再谨慎调优先级 |
| 驱动缓存/进程隔离改动大 | 会增加维护成本 | 只作为后续升级方案 |

## 10. 最终建议

当前最合理的判断是：

```text
陀螺仪读取路径本身足够快。
小车现在的问题主要是主程序高负载下，控制相关线程不能稳定按 5ms/8ms 被调度。
所以第一阶段不要急着重构陀螺仪驱动，而应该先减少日志、TFT、UDP 图传和图像处理对控制线程的干扰。
```

建议第一轮只做低风险优化：

| 优化 | 是否建议立刻做 |
|---|---|
| 高频日志限频/关闭 | 是 |
| `std::endl` 改掉或默认关闭 | 是 |
| gyro stale/timeout 阈值临时放宽 | 是 |
| UDP 图传限帧 | 是 |
| TFT 合并 flush | 是 |
| 控制线程优先级 | 第二轮 |
| 驱动缓存 | 第三轮 |
| 进程隔离 | 备用高级方案 |

最终验收标准：

| 指标 | 目标 |
|---|---:|
| `gyro_read_avg_ms` | `<1ms` |
| `gyro_age_ms` 常态 | `<10~20ms` |
| `gyro_timeout_count` | 基本不增长 |
| `I_freeze` | 大多数时间为 `0` |
| `dir_timer/speed_timer Timeout summary` | 明显减少 |
| 直道表现 | 不因控制卡顿出现明显左右摇头 |
| 转弯表现 | 保留当前优秀转弯性质 |
