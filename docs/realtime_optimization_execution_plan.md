# 小车实时性优化执行方案

> 来源：根据 `docs/realtime_optimization_report.md` 中的批注整理。  
> 目标：先做一轮低风险、可回退、可验证的实时性优化；暂不做大规模控制架构重构。

## 1. 批注理解

我对当前批注的理解如下：

| 主题 | 你的批注含义 | 执行结论 |
|---|---|---|
| 编码器采样/速度环周期 | 想评估 `1ms -> 2ms`、`3ms -> 4ms` 是否能提升实时性 | 第一批纳入执行，作为低风险减负项 |
| UDP | 图传默认关闭，但 UDP 波形是调车必须的 | 保留 `udp_send_string()` 波形，不关闭、不限流；只保持图传默认关闭 |
| 环岛日志 | 环岛很少进入，不必为了它专门关闭 | 不删除环岛日志，只把 `std::endl` 改成不强制 flush 的换行 |
| GYRO 日志 | 可以改低频 | 第一批把 `[GYRO]` 调试打印降频 |
| TFT 前端 | 现在主要看终端状态，希望默认关闭前端 UI | 增加 `front_UI_switch`，默认 `0`，启动时不初始化 TFT 和按键 |
| 主循环耗时统计 | 这个部分之后再说，不是当前重点 | 第一批不做主循环阶段耗时统计 |
| 架构级优化 | 按前面批注执行，不急着大改 | 暂不做线程优先级、驱动缓存、进程隔离 |

核心执行原则：

| 原则 | 说明 |
|---|---|
| 不影响调车必要链路 | VOFA 接收、UDP 波形发送、PID 参数修改必须保留 |
| 不改变控制算法主体 | 方向环、速度环、角速度环算法先不重写 |
| 先减少系统抖动源 | 降低高频 timer 压力、减少 flush、关闭 TFT 前端 |
| 保持安全停车能力 | 即使前端 UI 关闭，停车清零逻辑仍必须有效 |

## 2. 第一批执行范围

第一批只做以下改动：

| 编号 | 改动 | 是否执行 | 说明 |
|---|---|---:|---|
| E1 | 编码器平均采样周期 `1ms -> 2ms` | 是 | 降低 1ms timer 对系统的压力 |
| E2 | 速度环周期 `3ms -> 4ms` | 是 | 降低速度环调度频率，观察是否减少超时 |
| E3 | `std::endl` 改为普通换行 | 是 | 保留日志内容，但避免强制 flush |
| E4 | `[GYRO]` 调试打印降频 | 是 | 减少角速度环调试输出干扰 |
| E5 | 新增 `front_UI_switch`，默认关闭 TFT/按键前端 | 是 | 默认不初始化 TFT，不扫按键，不刷屏 |
| E6 | 新增 VOFA 发车/停车命令 | 是 | 前端关闭后仍能通过 VOFA 控制运行状态 |
| E7 | 保留 UDP 波形发送 | 是 | 调车必须，不关闭 |
| E8 | gyro 超时/stale 阈值临时放宽 | 是 | 减少高负载下误判和频繁冻结积分 |

第一批明确不做：

| 编号 | 暂不做内容 | 原因 |
|---|---|---|
| N1 | 不关闭环岛日志 | 环岛触发低频，按你的批注保留 |
| N2 | 不做 TFT 合并 flush 深改 | 先直接默认关闭前端 UI，更符合你的使用方式 |
| N3 | 不做主循环阶段耗时统计 | 你批注“这个部分再说” |
| N4 | 不改 UDP 波形发送频率 | 这是调车必须的数据链路 |
| N5 | 不做线程优先级调整 | 属于第二轮优化 |
| N6 | 不做 MPU6050 驱动缓存/进程隔离 | 当前 benchmark 证明硬件读取本身很快 |

## 3. 具体实现方案

### 3.1 编码器采样周期改为 2ms

当前状态：

| 项目 | 当前值 |
|---|---:|
| 定时器 | `encoder_ave_timer` |
| 周期 | `1ms` |
| 回调 | `encoder_sample_1ms_thread()` |
| 平均方式 | 3 点滑动平均 |

执行方案：

| 改动 | 方案 |
|---|---|
| 周期 | `encoder_ave_timer.set_seconds_ms(1, ...)` 改为 `2` |
| 函数名 | 第一批不强制重命名，避免牵扯过多；只改注释说明当前是 2ms 调用 |
| 滑动平均 | 仍保留 3 点平均 |
| 等效窗口 | 从约 `3ms` 变为约 `6ms` |

性能影响判断：

| 影响 | 判断 |
|---|---|
| CPU/timer 压力 | 会下降，1ms timer 压力减少约一半 |
| 速度反馈延迟 | 会略增，3 点平均窗口变成约 6ms |
| 对速度环稳定性 | 大概率可接受，但需要实车观察 |
| 如果变迟钝 | 第二轮再把平均窗口从 3 点改为 2 点，或调整速度环 PID |

验收：

| 指标 | 目标 |
|---|---:|
| `Timeout summary` | 比 1ms 时减少 |
| 速度波形 | 不出现明显阶梯或大延迟 |
| 起步/加减速 | 不明显变肉 |
| 直道表现 | 不因速度反馈延迟加重摇头 |

### 3.2 速度环周期改为 4ms

当前状态：

| 项目 | 当前值 |
|---|---:|
| 定时器 | `speed_timer` |
| 周期 | `3ms` |
| 回调 | `test_enc_and_motor_rps()` |

执行方案：

| 改动 | 方案 |
|---|---|
| 周期 | `speed_timer.set_seconds_ms(3, ...)` 改为 `4` |
| 控制函数 | 不改 `test_enc_and_motor_rps()` 内部算法 |
| PID 参数 | 第一批不自动修改 P/I/D |

性能影响判断：

| 影响 | 判断 |
|---|---|
| timer 压力 | 会下降约 25% |
| 速度环响应 | 理论上略慢，但 4ms 仍属于高频速度闭环 |
| 对陀螺仪实时性 | 间接有帮助，因为控制线程竞争减少 |
| 风险 | 如果速度环 PID 对 3ms 强依赖，可能需要微调 |

验收：

| 指标 | 目标 |
|---|---:|
| 速度环超时 | 减少 |
| 起步响应 | 不明显变差 |
| 编码器波形 | 不出现持续振荡 |
| 速度 PID | 如有变化，后续只微调，不先大改 |

### 3.3 保留 UDP 波形，不关闭调车链路

当前 UDP 分两类：

| 类型 | 当前用途 | 执行策略 |
|---|---|---|
| UDP 波形/状态 JSON | 发送速度、误差、PWM、PID 等调车数据 | 保留 |
| UDP 图传 | 发送 OpenCV/JPEG 调试图像 | 默认关闭 |

执行方案：

| 改动 | 方案 |
|---|---|
| `udp_timer` | 保持 `10ms` 周期不变 |
| `udp_send_string()` | 保留 |
| `#is_udp_img=0` | 保持默认关闭图传 |
| 图传限帧 | 第一批不新增，因为图传默认不用 |

注意：

```text
本轮优化不能为了降低负载把 UDP 波形关掉。
后续如果发现 10ms JSON 发送也造成负载，再单独讨论，但第一批不动。
```

### 3.4 `std::endl` 改为普通换行

当前需要处理的位置包括：

| 文件 | 典型输出 |
|---|---|
| `example/src/circle.cpp` | `begin`、`not circle`、`cross`、`in` |
| `main/front_ui.cpp` | `run`、`drive_by_enable` |
| `main/main.cpp` | 少量退出/调试输出 |

执行方案：

| 改动 | 说明 |
|---|---|
| `std::cout << xxx << std::endl` | 改为 `std::cout << xxx << '\n'` |
| 环岛日志内容 | 保留 |
| 前端日志内容 | 保留，但不强制 flush |
| 无意义脏话调试输出 | 如果仍在活跃路径，可改成正式提示或删除 |

为什么这样做：

| 原因 | 说明 |
|---|---|
| `std::endl` 会 flush | 每次输出都可能等待终端 |
| 普通 `'\n'` 不强制 flush | 仍换行，但实时性更好 |
| 保留环岛日志 | 符合你的批注，不影响偶发调试 |

验收：

| 指标 | 目标 |
|---|---|
| 编译 | 不引入语法错误 |
| 日志 | 内容仍能看到 |
| 实时性 | 不再因 `endl` 主动 flush |

### 3.5 `[GYRO]` 调试打印降频

当前状态：

| 位置 | 当前周期 |
|---|---:|
| `dir_pd.cpp` 中 `gyro_yaw_rate_control_print_debug(50)` | 方向环 `8ms * 50 ≈ 400ms` |

执行方案：

| 改动 | 建议值 |
|---|---:|
| `[GYRO]` 打印间隔 | `50 -> 100` |
| 等效时间 | `8ms * 100 ≈ 800ms` |

说明：

| 项目 | 结论 |
|---|---|
| 是否保留 GYRO 调试 | 保留 |
| 是否彻底关闭 | 不关闭 |
| 是否修改 `[DIR]` | 第一批暂不改，避免调方向时少信息 |

验收：

| 指标 | 目标 |
|---|---|
| `[GYRO]` 日志 | 约 0.8s 一条 |
| 调参可读性 | 仍能观察 `age/read/timeout/I_freeze` |
| 实时性 | 日志频率降低 |

### 3.6 gyro 诊断阈值临时放宽

当前建议：

| 参数 | 当前 | 第一批改为 |
|---|---:|---:|
| `kGyroReadTimeoutMs` | `50ms` | `100ms` |
| `kGyroStaleFreezeMs` | `30ms` | `60ms` |

执行理由：

| 理由 | 说明 |
|---|---|
| benchmark 已证明读取本身很快 | 当前超时更多是调度延迟 |
| 50ms/30ms 容易在高负载下误报 | 会导致 `I_freeze` 频繁出现 |
| 第一轮目标是稳定观察 | 先减少误判，再逐步压回更严阈值 |

风险：

| 风险 | 应对 |
|---|---|
| 阈值变宽可能掩盖真实卡顿 | 继续观察 `gyro_age_ms` 和 `Timeout summary` |
| 数据旧时控制更久使用旧值 | `60ms` 只是第一轮调试值，稳定后可再收紧 |

### 3.7 新增 `front_UI_switch`，默认关闭前端 UI

你的批注是“直接关闭前端 UI，现在都是直接在终端上看状态”。  
这里要特别注意：当前 `front_ui` 不只是屏幕显示，还维护 `car_running`、停车清零、K2 发车等状态。

所以执行时要分成两层：

| 层 | 是否关闭 | 说明 |
|---|---|---|
| TFT 初始化 | 默认关闭 | 不打开 `/dev/LQ_TFT_1.8` |
| 按键 GPIO 初始化 | 默认关闭 | 不初始化 K0/K1/K2 |
| 屏幕刷新 | 默认关闭 | 不调用 draw/flush |
| `car_running` 状态 | 不关闭 | 速度环/方向环仍依赖它 |
| 停车清零 | 不关闭 | 安全逻辑必须保留 |

执行方案：

| 改动 | 方案 |
|---|---|
| 新增变量 | `volatile int front_UI_switch = 0;` |
| 默认值 | `0`，表示前端 UI 关闭 |
| 头文件声明 | 在 `front_ui.hpp` 暴露 `front_UI_switch` |
| 初始化 | `front_ui_init()` 中若 `front_UI_switch == 0`，跳过 TFT 和按键初始化 |
| 轮询 | `front_ui_poll()` 中若 `front_UI_switch == 0`，直接返回 |
| 显示 | `draw_ui()` 只在 UI 开启且 ready 时执行 |

实现细节要求：

| 细节 | 原因 |
|---|---|
| 按键 `ls_gpio` 不应继续作为文件作用域静态对象直接构造 | 否则即使 UI 关闭，程序启动时仍可能初始化 GPIO |
| K0/K1/K2 对象改为延迟初始化 | 只有 `front_UI_switch == 1` 时才创建 |
| `front_ui_is_running()` 仍返回 `car_running` | 保持速度环/方向环逻辑不变 |
| `front_ui_hold_stop()` 仍能清零电机 | 保持安全停车 |

第一版不做：

| 不做项 | 原因 |
|---|---|
| 不支持运行中热启 TFT | 默认关闭即可；热启会增加复杂度 |
| 不重写 UI 绘图接口 | 既然默认关闭，合并 flush 暂不急 |

### 3.8 前端关闭后，新增 VOFA 发车/停车命令

如果前端 UI 默认关闭，K2 不再扫描。为了不让车永远停住，需要新增 VOFA 运行命令。

执行方案：

| 命令 | 行为 |
|---|---|
| `#run=1;` | 发车：`car_running = true`，重置 gyro 控制状态，更新 `last_start_time` |
| `#run=0;` | 停车：清零目标速度、方向输出、PWM，并取消脚本 |

设计细节：

| 细节 | 说明 |
|---|---|
| `#run=1;` 不覆盖当前 `#spd` | 避免发车时把 VOFA 设好的速度改回屏幕策略速度 |
| `#run=0;` 使用统一停车函数 | 避免停车清零逻辑散落多处 |
| K2 发车逻辑保留 | 如果以后 `front_UI_switch=1`，按键仍可用 |

推荐使用方式：

```text
#spd=10;
#gyro=1;
#run=1;

停车：
#run=0;
```

可选扩展：

| 命令 | 是否第一批做 | 说明 |
|---|---|---|
| `#target=1;` / `#target=0;` | 建议做 | 前端关闭后 K0 不可用，需要 VOFA 控制目标板脚本开关 |
| `#front=1;` | 暂不做 | 运行中热启 TFT/按键复杂，先不加 |

## 5. 执行顺序

建议严格按顺序做，方便出问题时回退：

| 顺序 | 操作 | 验证 |
|---|---|---|
| 1 | 改 `std::endl` 为普通换行 | 编译通过，日志仍可见 |
| 2 | 改 GYRO 打印频率和 gyro 阈值 | `#gyro=1` 后日志更低频 |
| 3 | 改编码器/速度环周期 | 观察 `Timeout summary` 是否减少 |
| 4 | 增加 `front_UI_switch` 默认关闭 UI | 启动时不再初始化/刷新 TFT |
| 5 | 增加 `#run` 发车/停车命令 | 前端关闭时仍能 VOFA 发车停车 |
| 6 | 可选增加 `#target` 命令 | 前端关闭时仍能控制目标板脚本开关 |
| 7 | 实车测试 | 对比 gyro age、timeout、直道稳定性 |

## 6. 测试方案

### 6.1 编译前静态检查

| 检查 | 标准 |
|---|---|
| `git diff --check` | 无空白错误 |
| 搜索 `std::endl` | 活跃运行路径基本不再使用 |
| 搜索 `front_UI_switch` | 默认值为 `0` |
| 搜索 timer 周期 | 编码器 `2ms`，速度环 `4ms` |

### 6.2 上车基础测试

按顺序执行：

```text
#spd=0;
#gyro=0;
#run=1;
```

验收：

| 项目 | 期望 |
|---|---|
| 小车 | 不动 |
| 速度环 | 可以运行但目标为 0 |
| PWM | 不应异常增大 |
| 终端 | 不应出现 TFT 相关错误 |

然后：

```text
#spd=5;
#run=1;
```

验收：

| 项目 | 期望 |
|---|---|
| 小车 | 低速运行 |
| UDP 波形 | 正常显示速度、误差、PWM |
| 前端 UI | 默认不显示、不刷屏 |
| 停车 | `#run=0;` 能立即停车 |

### 6.3 角速度环测试

```text
#spd=5;
#gyro=1;
#run=1;
```

观察：

| 字段 | 目标 |
|---|---:|
| `gyro_read_avg_ms` | `<1ms` |
| `gyro_age_ms` | 多数 `<20ms`，不应长期大于 `60ms` |
| `gyro_timeout_count` | 不应持续增长 |
| `I_freeze` | 大多数时间为 `0` |
| `Timeout summary` | 比修改前减少 |

### 6.4 周期调整验证

重点比较修改前后：

| 对比项 | 预期 |
|---|---|
| 编码器波形 | 可能更平滑，但不能明显滞后 |
| 速度环输出 | 不应出现更大振荡 |
| 直道摇头 | 至少不能变差 |
| timer 超时 | 应减少 |
| CPU 占用 | 应下降一点 |

如果出现问题：

| 问题 | 回退策略 |
|---|---|
| 起步明显变慢 | 速度环 `4ms -> 3ms` 回退 |
| 速度波形延迟明显 | 编码器 `2ms -> 1ms` 回退，或滑动平均 3 点改 2 点 |
| 直道摇头变大 | 优先回退速度环周期，再检查 PID |
| VOFA 无法发车 | 检查 `#run` 是否正确设置 `car_running` |

## 7. 最终验收标准

| 指标 | 验收标准 |
|---|---|
| 默认启动 | 不初始化 TFT/按键前端，不刷屏 |
| VOFA 调车 | `#spd/#gyro/#run` 可正常使用 |
| UDP 波形 | 保持 10ms 状态发送，不被关闭 |
| 停车安全 | `#run=0` 和内部停车逻辑都能清零电机 |
| 日志 | 环岛日志保留，`std::endl` 去除，`[GYRO]` 降频 |
| 控制周期 | 编码器 2ms、速度环 4ms 后不明显降低行驶性能 |
| 角速度环 | `age/timeout/I_freeze` 比修改前稳定 |
| 可回退性 | 每项都能单独回退，不和大重构绑定 |

## 8. 后续暂缓项

这些先不做，等第一批实车结果出来后再决定：

| 暂缓项 | 触发条件 |
|---|---|
| 主循环阶段耗时统计 | 如果第一批后仍有明显超时 |

| UDP 图传限帧 | 如果调试时需要长期打开图传 |
| 控制线程优先级 | 如果减负后仍有 timer 超时 |
